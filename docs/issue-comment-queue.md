# Issue 评论与连续搭建

同一个 Issue 对应同一个工作分支和 PR。当前轮 Actions 完整结束后，评论按评论 ID 顺序逐条处理，不等待 PR 合并。只有仓库所有者在自己创建的任务 Issue 中发表的评论会进入队列；PR 评论、机器人评论和其他用户的评论不触发模型调用。

## 追加搭建指令

在原 Issue 里发表评论，第一行独立写 `/build`，下面写 prompt：

```text
/build

在现有采购系统上增加供应商评分。
订单完成后采购员可提交评分，首页显示前五名供应商。
验收：采购员不能修改其他人的评分。
```

当前轮运行期间可以连续追加多条。每轮从已有工作分支 HEAD 继续实现、验收，再更新原 PR。队列保存评论 ID、状态和展示摘要，不把入队时的内容当作执行依据。每轮 Actions 的 prepare 阶段重新读取最新 Issue 正文和原评论，再组装本轮 prompt。因此，尚未执行时编辑正文或评论会生效；修改 `/build` 前缀也会改变本轮是搭建还是问答。删除或清空待执行评论会取消该条。

已经进入执行的单次运行使用启动时读取的内容，不在中途热替换；新的 checkpoint 接续运行会重新读取。已经完成的评论编辑后不会自动重跑，需要新增评论明确要求再做。原始运行输入保存在该 run 的 metadata artifact 中，仅供追溯。

## 问题与讨论

普通评论不需要命令，例如：

```text
现在的供应商评分权限是怎么控制的？采购员能看到其他人的评分吗？
```

这类评论进入问答轮次。Agent 基于当前分支代码回答，不执行搭建、安装依赖、启动应用或发布代码。模糊的修改请求会在回复中解释方案，并提示用 `/build` 明确提交。问答不改变 Issue 的搭建状态标签。

每条入队评论都有一条带原评论链接和引用的状态回执。处理结束后，Agent 单独发表带原评论链接、引用与回答的回复；搭建指令的回复解释本轮实现结果，问题的回复回答问题。GitHub Issue 没有 PR review 那种嵌套回复线程，这里用引用和永久链接建立对应关系。机器人回复不会再次进入队列。

后续轮次会获得当前 Issue 需求、先前评论的当前文本和 Agent 回复作为背景。先前评论可能被编辑，历史回复也可能过时，不能据此声称已按新文字重新执行。当前代码是已实现能力的依据；先前失败的指令不能当作已完成。

## 执行与恢复

- 初次实现与追加搭建都使用原有的完整验证和发布流程；已有分支不会导致追加指令跳过实现。
- 五小时 checkpoint 的自动接续属于同一条指令，完成后才处理下一条评论。
- 失败、取消或超时的轮次结束后，继续处理下一条评论。下一轮从已保存的分支继续；失败 runner 内没有发布的临时修改不会自动混入后续指令。
- PR 或 Issue 关闭后，尚未执行的搭建指令会被拒绝，避免创建第二个 PR；普通问题仍可回复。合并仍由人执行。
- 回执保存在 Issue 的机器人评论中，不依赖临时数据库或短期 artifact。不要编辑或删除回执与隐藏的 claim 评论。
- 重复事件不会重复入队。调度失败超过五分钟后，下一次协调会重试同一评论；工作流用独立 claim 防止重复实现。
- 评论编辑会刷新待执行队列；`workflow_run.completed` 触发下一轮调度；十五分钟定时扫描兜底处理漏掉的事件。也可在 Actions 的 **Comment build queue** 中手动输入 Issue 编号协调队列。
- Agent 问答失败时，该轮仍会有带结论的状态回执；不会伪造回答。可以发新评论重试。

新增 workflow 必须先进入仓库默认分支才会响应事件。上线后，每个 Issue 从第一条新发表的仓库所有者评论开始接入队列，不会自动回放此前的历史讨论；接入后的后续评论由定时扫描补漏。

## 控制面边界

队列调度器和回复发布器只执行默认分支的工厂代码。模型所在的问答 job 没有 `issues:write` 或 GitHub 写入 token；仅产生回复 artifact，由独立发布 job 读取后发表评论。问答工作区不会传给代码发布器，即使 Agent 违反只读指令产生本地修改，也不会更新应用分支。

这是工厂控制面功能，不是应用内的 Workflow/Notification 插件能力。业务 Agent 仍然不能修改 `.github/` 或自行调用 GitHub 发布接口。
