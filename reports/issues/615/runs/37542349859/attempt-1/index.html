问题 01 · 实现阶段

实现轮未写入任何业务代码，应用语言测试是唯一可见失败

本任务已处理

工作区相对 develop 基线只有未跟踪的 `client/extensions/nocobase-ai/`（AI Registry 扩展），没有资料/助手页面、路由、迁移、服务或种子；`agent-implement.jsonl` 的 978 条 bash 调用中没有一次写文件，仅重复执行 Registry 安装脚本；验证因此只在被安装扩展触发的语言覆盖率测试上失败。

原因（实现者自述）
实现 Agent 长时间处于命令重试/读取循环，未进入编辑阶段，业务功能没有落地。
处理方式
本轮补齐业务实现：`database/main/migrations/202609010001_create_materials.ts` 建资料表，`database/seed-data/*` 与 `database/main/seeds/202609250001_materials_initial_data.ts` 建三份资料、主管/同事账号与两档权限集；`server/{authorization,services,providers,routes,ai}` 提供权限范围、服务、HTTP 路由与只读工具/员工；`client/pages/{materials,assistant}` 与 `client/routes.ts`、`client/locales/*` 提供页面、路由和文案。权限范围条件与 `.ts` 导入两个真实阻塞一并修复（见下）。
影响 / 代价：实现轮约 31 分钟后被验证阶段终止；本轮重建业务功能，并新增 1 个集成测试（246 个测试全绿）。来源：Agent · retro.json
问题 02 · 修复阶段

app-locale-coverage 将 AI 扩展的组件文案当作应用文案

本任务已处理

`tests/logic/app-locale-coverage.test.ts` 报 139 个 `t('...')` 键缺失于 `client/locales/{en-US,zh-CN}.ts`，全部来自 `client/extensions/nocobase-ai/components/**`。

原因（实现者自述）
该测试跳过 `locales/` 目录和调用 `useTranslation('<literal>')` 的文件，而 AI 扩展的组件通过 `useAITranslate()` 读取自己的 `client/extensions/nocobase-ai/locales/*` 字典，既不在 `locales/` 目录下也不匹配命名空间规则，于是它的键被要求出现在应用语言资源里。另外该扩展自身也漏了 4 个组件正在使用的键（`tool.output`、`tool.businessReport.chartFailed`、`tool.businessReport.previewUnavailable`、`tool.businessReport.failed`），所以即使只补应用侧也不够。
处理方式
把扩展的 en-US/zh-CN 字典导入 `client/locales/{en-US,zh-CN}.ts`（同一份文案只维护一次），并把上述 4 个键补进扩展字典；未修改测试。
影响 / 代价：修复轮 1 次改动；重跑目标测试、相关 i18n 组件测试、全量 vitest 及 `pnpm build` 各 1 次。来源：Agent · retro.json
问题 03 · 修复阶段

布尔字段可见性条件用 `$eq false`，查询期报 FIELD_CAPABILITY_NOT_SUPPORTED

本任务已处理

同事读取资料列表时服务端报错，直连数据库能查到资料，但 `/api/materials` 与助手工具都取不到数据；错误为 `Operator "$eq" is not supported for Field "restricted" of type "boolean".`。

原因（实现者自述）
`@nocobase/db` 的 Repository 在查询时才按字段类型校验算子：布尔字段只允许 `$isTruly`/`$isFalsy`/`$empty`/`$notEmpty`，而授权权限集里保存的数据范围条件写成了 `condition('restricted', '$eq', false)`。条件按名保存、运行期才解析，所以只有真正查询时才暴露。
处理方式
把 `server/authorization/materials.ts` 的可见性条件改为 `condition('restricted', '$isFalsy')`；已保存的权限集按名引用该条件，重启即生效，无需重新播种。
影响 / 代价：1 处改动 + 重启；用真实 HTTP 复核了同事只看到 2 条、主管看到 3 条。来源：Agent · retro.json
问题 04 · 修复阶段

应用 `database/**` 用 `.js` 相对导入，Node 原生 TS 加载报 ERR_MODULE_NOT_FOUND

本任务已处理

种子/迁移从源码以原生 TS 被 Node `import()` 加载时，`import '../../server/authorization/materials.js'` 找不到模块；而 vitest/编译产物下同样的 `.js` 写法正常。

原因（实现者自述）
Node 原生类型剥离不把 `.js` 说明符重写成 `.ts`，所以源码树里不存在对应 `.js`；`tsconfig.server.json` 通过 `allowImportingTsExtensions` + `rewriteRelativeImportExtensions` 支持 `.ts` 说明符并在编译时改写为 `.js`，但只对以 `.ts` 书写的导入生效。
处理方式
把应用自有 `database/**`（迁移外的种子与 `database/seed-data/*`）的相对导入统一改为 `.ts`；`server/**` 仍走 vitest/编译，保持 `.js`。
影响 / 代价：3 处导入改写；用 `tsc -p tsconfig.server.json` 与 `db apply` 各验证一次。来源：Agent · retro.json
问题 05 · verification

cookie 写入被 INVALID_CSRF_ORIGIN 拦截，未配置 publicOrigin 时授权从未被执行

本任务已处理

用 curl 以会话 cookie 调 POST/PATCH/DELETE `/api/materials` 一律 403 `INVALID_CSRF_ORIGIN`（domain=authentication），看起来像权限拒绝；在新增集成测试里主管的写请求也返回 403，而主管本应有 manage 权限。

原因（实现者自述）
`auth.required()` 在 cookie 写入时先做 CSRF/Origin 校验，Better Auth 的 `trustedOrigins` 来自静态配置的 `baseURL`，而 `baseURL` 取自应用的 `app.publicOrigin`。未设置时无法信任请求来源，写请求在校验阶段就被拒绝，授权中间件根本不会执行。
处理方式
验证环境给应用配置 `APP_PUBLIC_ORIGIN`（本地临时配置用 `app.publicOrigin: http://127.0.0.1:13100`，集成测试用 `env: { APP_PUBLIC_ORIGIN: 'http://localhost' }`），并带上匹配的 `Origin` 头；随后同事写请求得到真正的 `AUTHORIZATION_DENIED`（No grant allows materials.manage），主管写请求 200。
影响 / 代价：1 次额外重启 + 集成测试 1 个 env；确认了写路径 403 的来源确实是授权而非 CSRF。来源：Agent · retro.json

建议 01 · 验收机制

AI Registry 扩展的自带字典缺少组件实际引用的键

可自动化

`@nocobase/app-plugin-ai-employee` 的 `nocobase-ai` Registry item 中，`components/chat/tool-call-card.tsx`、`components/tools/business-report-*.tsx` 调用了 4 个不存在于其 `locales/en-US.ts` / `zh-CN.ts` 的键。`useAITranslate` 会回退到组件里的英文 fallback，因此中文界面会显示英文，而普通 typecheck 也发现不了（`zh-CN.ts` 是 `as const`，未按 en-US 校验完整性）。

建议改动

在发布 Registry item 前，用与 `tests/logic/app-locale-coverage.test.ts` 相同的方式扫描 `components/` 的 `t()` 键并与其 `locales` 字典比对；或把 item 的 `zh-CN.ts` 标注为 `Record<NocoBaseAITranslationKey, string>` 让缺失键成为编译错误。

来源：Agent · retro.json

建议 02 · Skill 与文档

安装 AI 扩展后没有说明它如何与应用语言资源共存

需人工判断

`nocobase-app-plugin-ai-employee` 的 `chat-surfaces.md`「After installing」只要求跑应用的 lint/typecheck/test，未提示扩展组件使用 `useAITranslate` + 自带字典、会被 `app-locale-coverage` 当作应用键。实现 Agent 因此直到验证阶段才遇到这 139 个键。

建议改动

在该节补一句：扩展自带 `locales/` 字典，应用需把这些字典并入 `client/locales/*`（或在覆盖率测试中按扩展命名空间排除），并给出本应用采用的导入做法。

来源：Agent · retro.json

建议 03 · dx

布尔字段非法算子只在查询期报错

可自动化

`OPERATORS_BY_TYPE.boolean` 只含 `$isTruly/$isFalsy/$empty/$notEmpty`，但 `condition('restricted', '$eq', false)` 能顺利构建并在权限集里保存，直到真实查询才抛 `FIELD_CAPABILITY_NOT_SUPPORTED`。授权数据范围按名保存、运行期解析，使这类错误更晚才暴露，且看起来像“查不到数据”而非配置错误。

建议改动

在 Collection Builder 或 `condition()` 构建时按字段类型校验算子并立即抛错；或为布尔字段暴露类型收窄的谓词（如 `booleanField.isFalse()`），从 API 上杜绝 `$eq`。

来源：Agent · retro.json

建议 04 · Skill 与文档

应用 database/** 相对导入必须用 .ts 扩展名，文档未强调

可自动化

Node 原生 TS 类型剥离不把 `.js` 说明符解析到 `.ts`，所以从迁移/种子源码 import 同仓库 `.ts` 文件必须写 `.ts`；`tsconfig` 的 `rewriteRelativeImportExtensions` 会在编译时改回 `.js`。写成 `.js` 时 vitest/编译产物正常，只有 `db apply` 等原生加载才失败，定位成本高。

建议改动

在 `nocobase-app-development` / `nocobase-db` 的迁移与种子参考中明确：应用自有 `database/**` 的相对导入使用 `.ts`，`server/**` 使用 `.js`；可加一条针对 `database/**` 的 lint 规则自动检查。

来源：Agent · retro.json

建议 05 · 验收机制

测试 harness 未给应用配置 publicOrigin，cookie 写入会先被 CSRF 拒绝

可自动化

`@nocobase/app-testing/server` 生成的测试配置不设置 `app.publicOrigin`，Better Auth 因此没有可信来源；任何用会话 cookie 触发 `auth.required()` 的写请求都会 403 `INVALID_CSRF_ORIGIN`，让“无权限应 403”的断言因错误原因通过，真正授权路径未被覆盖。

建议改动

测试 harness 默认给应用一个 `APP_PUBLIC_ORIGIN`（如 `http://localhost`）作为测试来源，或在文档中要求写路径测试显式设置；断言 403 时校验 `reason`/`domain` 为 `AUTHORIZATION_DENIED`。

来源：Agent · retro.json
