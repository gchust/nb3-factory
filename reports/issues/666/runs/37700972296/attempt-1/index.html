问题 01 · 实现阶段

Workflow run modules cannot import application server code

本任务已处理

The ticket-acceptance workflow failed at runtime with `Run module "../../../server/service/ticket-service.js" resolves outside its artifact`, and a temporary test showed `Cannot find module '/tmp/.../storage/workflows/server/service/ticket-service.js'`.

原因（实现者自述）
A workflow artifact is materialized into a content-addressed copy under storage/workflows/<key>/<digest>/ and the loader enforces containment, and bare package imports are not reliably resolvable from that copy, so handler modules must be self-contained. The app registered its service under a token created by createServiceToken('...'), whose value is a fresh object, so even a handler that described the same token name would hold a different Map key.
处理方式
Added workflows/ticket-acceptance/server/tokens.ts which derives the token from a process-global Symbol.for('equipment-service/service.ticket'), and changed server/service/ticket-service.ts to use the same Symbol.for literal. The app container and the artifact copy now resolve one service. Handlers keep type-only imports for their flow context and use a structural port instead of importing the service class.
影响 / 代价：未提供，不估算来源：Agent · retro.json

问题 16 · 修复阶段

Repeating an acceptance decision ran the acceptance workflow again and duplicated the log and message

本任务已处理

A second POST /service/tickets/:id/accept for the same pendingAcceptance ticket returned 200 and drove the acceptance workflow to run again, appending another accepted success log and another ticket.assigned in-app message to the engineer; the business requirement is that a repeated status request must not advance state or send a duplicate business message.

原因（实现者自述）
requestAcceptance built its workflow eventKey from Date.now(), so every call was a brand-new event and the workflow eventKey dedupe never engaged. The workflow itself also had no ticket-state guard, so even a repeated decision re-applied the update and re-notified.
处理方式
requestAcceptance now reads the ticket first and short-circuits: it answers {status: already-accepted} when decision.accept and ticket.acceptedAt, or {status: already-refused} when !accept and the ticket is closed, without triggering the workflow. The skipped branch uses a stable eventKey (ticket-acceptance:${ticketId}:workflow-skipped). recordStep keeps one row per (eventKey, status) and applyAcceptance is a no-op when the ticket is already past pendingAcceptance, so a genuine retry still runs but a repeat cannot duplicate the log or the assigned message. No separate retry endpoint: the ticket-detail Accept action plus the workflow run record are the recovery path, and a genuine failure keeps a real failed step. Added a test that accepts once, repeats twice, and asserts one accepted:success log, no failed log and one assigned message.

建议 01 · skill/documentation

Document that a source-booting test must register the TypeScript loader once a seed imports server code

可自动化

The application-development Skill and the seed reference state that a seed may import server/*.js. That is correct for `pnpm dev` and `pnpm nocobase`, both of which run under tsx, but a test that boots from source with seeds.autoRun and no loader fails on the first nested .js specifier. The template's own app-server.test.ts is such a test, so an application that adds a migration+seed following the documented pattern breaks a shipped test.

建议改动

Add a note to references/testing.md and the seed guidance: a test that installs from source and runs seeds must call register() from 'tsx/esm/api' before booting, with the two template test files as examples. Optionally call this out in the migration/seed scaffold so authors add it with the first seed.

建议 02 · framework/authorization

Fail fast when a read/update/delete grant omits recordAccess

可自动化

A data grant without a record-access rule is accepted at registration and then silently denies with NO_RECORD_ACCESS at request time. This cost a debugging cycle because the permission set looked complete.

建议改动

Validate at permission-set registration that every read/update/delete grant names a record-access rule (the built-in allRecords counts) and throw with the collection/action named. Keep create exempt.

建议 03 · framework/service-provider

Provide a documented process-global service token helper

可自动化

createServiceToken(name) returns a fresh object, so a service registered by the application is unresolvable from another module instance that recreates the token — which is exactly what a materialized workflow artifact is. The only workaround is Symbol.for with a hand-shared string literal, which is easy to get wrong and is invisible to the type checker.

建议改动

Export a helper such as globalServiceToken(name) that derives Symbol.for(name) and a ServiceToken<T>, and document it as the way to share a service across workflow artifacts, plus a note that two createServiceToken calls with one name are different keys.

建议 04 · framework/workflow

Let an application declare a workflow revision active on boot

可自动化

Materialization produces an enabled:false, non-current revision. Triggering a workflow that the application itself ships requires reaching into the internal workflow service via a structural cast, or manipulating the workflows table directly. Both are unsupported surfaces.

建议改动

Expose a public enable/activate call on the workflow service contract (or a registration option on the plugin) so an application can declare its own workflow active without touching internals.

建议 05 · tooling/lint

Resolve the no-base-to-string / no-unnecessary-type-assertion conflict for repository scalars

可自动化

Repository rows expose fields as unknown. String(value) triggers @typescript-eslint/no-base-to-string, while String(value as string) triggers no-unnecessary-type-assertion because String() accepts any type. The two rules leave no assertion that satisfies both, so every call site needs a typeof-narrowing helper.

建议改动

Have RepositoryRecord expose a narrow scalar union (string|number|boolean|null) for scalar fields, or ship a documented coercion helper in the db package that call sites can import instead of String().

建议 06 · framework/routing

A navigation group's path is silently prepended to absolute child paths

可自动化

An app route group that declares a path AND children declared with absolute paths registers each child twice under the group prefix (e.g. /service/service/tickets), and a child record route gets doubled again. Nothing warns; the backend answers and every URL 404s/redirects to home, which reads as a broken feature rather than a route-declaration mistake. This made the whole ticket-detail workflow unreachable.

建议改动

At registration, detect a child path that already starts with its parent group's path and either normalize it or throw with the route id and both paths named. Alternatively document prominently that a group either declares a path and children use relative segments, or declares no path and children carry the full path.

建议 07 · framework/database

The shared timestamp helper assumes every collection has updatedAt

可自动化

touched() writes updatedAt on update. A collection that intentionally has no updatedAt (an append-only inbox like service_messages, with only read/read_at) fails at request time with 400 FIELD_NOT_FOUND 'updatedAt' does not exist, and the error names a field the author never declared.

建议改动

Let a collection declare its timestamp fields (or have the helper inspect the schema and write only columns that exist), and have the Collection Builder record createdAt/updatedAt presence so touched() can fail at registration instead of per request.

建议 08 · framework/api-client

api.request returns the whole envelope while the data hooks unwrap it

可自动化

useServiceList/useServiceObject destructure { data }, but api.request resolves to { data, meta }. Three separate pages stored the envelope and then read one level too high, producing browser crashes (TypeError …map) or blank results. The same call looked correct in both styles, so the mistake recurs.

建议改动

Make the contract single: either api.request resolves to the parsed envelope everywhere and the hooks stop unwrapping, or add a typed helper such as api.requestData() that returns data only, and document the one true shape in the client reference.

建议 09 · framework/plugin-boundary

Self-service plugin pages cannot be extended with a trusted administrative operation

需人工判断

The API Keys plugin's page is a settings page (not an App route), so route overrides and source extensions cannot touch it, and its client calls self-service Better Auth endpoints that only act on the caller's own keys — a supervisor or admin gets 404 when revoking another account's key. The only fix is for the application to reimplement a management surface using the plugin's server ApiKeyService.

建议改动

Either mark the settings page overridable (allow a route override for settings pages) or give the plugin an option/hook for a trusted server-side list/revoke that an application can wire into its own administration page. Document that settings pages are otherwise off-limits to overrides.

建议 10 · framework/scheduler

An on-demand trigger does not honor the schedule's enabled state

可自动化

Disabling a schedule through the Scheduler HTTP API stops the clock but the application's manual 'run now' button still produced new results, violating 'a disabled controlled run produces no new results'. The scheduler exposes enable/disable but no way for a target to ask whether its schedule is currently runnable.

建议改动

Expose the enabled/runnable state of a schedule to registered targets (or refuse to resolve a disabled schedule's target), and document that a manual trigger must check it. Alternatively provide a public scheduler API for 'run this schedule now' that enforces the flag.
