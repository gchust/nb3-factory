问题 01 · 修复阶段

实时通道握手挂起时，整个应用被会话准备门槛挡住

处理结果未提供

登录成功后页面停在 Preparing your session…，约 10 秒后显示 Unable to connect / The realtime connection could not be prepared. Retry to enter the application, or sign out.；同一账号用全新浏览器配置登录正常，QA 的浏览器现场已不可得。

原因（实现者自述）
应用初始化时为通知订阅建立 WebSocket，但客户端没有握手/连接超时；反向代理或浏览器连接池让升级请求一直停在 CONNECTING 时，realtime.active 仍为 true 且 onOpen 永不触发，SessionPreparation 的 10 秒兜底把可选的实时通道当成进入应用的必要条件。服务端日志、权限接口和 HTTP 请求均正常，因此不是服务端拒绝或业务接口故障；QA 环境中升级请求为何挂起无法从现有现场确认，但该机制能稳定复现同一错误。
处理方式
在 client/routing/session-preparation.tsx 增加默认关闭的 allowRealtimeUnavailable；应用在 client/app.ts 显式开启。准备失败时仍挂载业务页面，由 HTTP 授权正常解析权限，只在底部显示“Live updates are unavailable”状态条和重试按钮（重载文档以释放卡住的连接）。默认关闭保留 shell 原有的 fail-closed 重试/退出行为。用本地反向代理挂起 WS 升级复现了原错误，并验证工单页/仪表盘可进入；新增组件测试覆盖降级进入，原 10 秒超时和重试/退出测试未改动。
影响 / 代价：多轮复现与临时反向代理验证；修复轮 1 次。来源：Agent · retro.json
问题 02 · repair-2

页头没有收件箱入口，实时通道失败后也没有可用的通知刷新路径

处理结果未提供

员工、工程师和服务台登录后页头只有主题与账号菜单，任何角色都看不到未读通知；实时通道不可用时页面只显示持久告警，也没有替代的定时刷新。

原因（实现者自述）
收件箱页面已有路由和 InboxBlock，但 client/layouts/components/header-actions.tsx 只渲染 ThemeSettings 与 UserMenu，从未把收件箱入口放进 shell；第一轮的实时降级只保留 HTTP 授权，没有为通知查询增加轮询。
处理方式
新增 client/layouts/components/header-inbox.tsx，在页头使用通知插件的 useInboxUnreadCount 与 InboxButton 展示未读数，并每 15 秒 invalidate inboxKeys.all，使页头角标和收件箱页面在 WebSocket 不可用时仍能更新；无 QueryClient 的组件测试环境退化为普通链接。移除 session-preparation.tsx 中“Live updates are unavailable”持久告警，保留 HTTP 授权降级。浏览器验证页头出现 Inbox 链接、未读角标，通知可点击进入 /helpdesk/tickets/:id。
影响 / 代价：1 个新组件、1 处 shell 接线、1 处降级 UI 删除；相关布局与收件箱测试通过。来源：Agent · retro.json
问题 03 · repair-2

处理人下拉包含服务台账号，而不是只有工程师

处理结果未提供

服务台分配工单时，处理人候选中同时出现服务台账号 Carol Desk 与工程师，容易把工单分配给不处理工单的角色。

原因（实现者自述）
GET /api/helpdesk/assignees 直接列出用户后再按用户名手工排除服务台，没有按应用角色 helpdesk-engineer 过滤，新增服务台或改名后过滤就会失效。
处理方式
路由改为 users.list({ roleScope: app, role: helpdesk-engineer, status: enabled, pageSize: 200 })，只返回启用中的工程师。运行中的 API 验证仅返回 engineer@example.com（Helpdesk Engineer）。
影响 / 代价：服务端过滤 1 处；浏览器分配流程沿用原下拉，无需改客户端。来源：Agent · retro.json
问题 04 · repair-2

工单与评论接口只返回用户 ID，页面显示 User <id> / System，且缺少逐工程师工作量

处理结果未提供

工单详情和评论里的报修人、处理人、评论作者显示 User 39342199 之类的原始 ID，系统评论作者显示 System；仪表盘只有状态/优先级/分类统计，没有每名工程师的处理量。

原因（实现者自述）
客户端已按 reporterName、assigneeName、authorName 渲染，但服务端路由从未解析这些字段；仪表盘接口也没有按工程师角色聚合被分配工单。
处理方式
在 server/routes/helpdesk.ts 增加 personNames/withPeople/namedComments，通过 userManagementServiceToken 解析姓名并在列表、详情、创建、评论响应中返回；生命周期历史也补充 actorName。仪表盘新增 workload，按 helpdesk-engineer 角色统计 processing/resolved/closed/total，客户端新增 Engineer workload 表格。API 返回 Helpdesk Employee/Helpdesk Engineer 与 workload 计数，浏览器详情不再出现 User <id>；仪表盘同时将 Open 指标明确标为 Unassigned/待分配，便于服务台看到未分派队列。
影响 / 代价：服务端姓名解析与聚合、客户端工作量卡片；tsc 与相关测试通过。来源：Agent · retro.json
问题 05 · repair-2

分配、处理进展与逾期提醒的收件人和内容不符合流程

处理结果未提供

没有“记录进展”通知；逾期提醒页面文案说通知处理人，而需求要求提醒服务台；通知无法验证是否能点击回到工单。

原因（实现者自述）
progress 转移没有绑定通知 effect；notifyOverdue 的收件人包含 assignee；各通知虽然写入 route target，但页头没有入口导致用户无法发现。
处理方式
为 progress 增加 notifyProgress effect，收件人为报修人与服务台并去重，正文包含进展备注；notifyOverdue 只发给服务台；服务端补充 progress 中英文文案，提醒设置页文案改为服务台。验证 progress 后 4 秒内生成两条 in-app 通知，target 为 {"type":"route","path":"/helpdesk/tickets/<id>"}，浏览器从收件箱点击可进入对应工单。
影响 / 代价：1 个 lifecycle effect、逾期收件人收敛、2 组服务端文案与 1 处客户端文案。来源：Agent · retro.json
问题 06 · repair-2

仪表盘逾期数在提醒发出后立即归零

处理结果未提供

处理中工单超过 24 小时后会触发提醒，但提醒转移把 statusChangedAt 更新为当前时间，仪表盘 Overdue 随即回到 0，服务台看不到仍在等待处理的逾期工单。

原因（实现者自述）
逾期条件只比较 statusChangedAt 与阈值，而 remind 是 processing→processing 的转移，生命周期会刷新状态变更时间；通知发出反而清除了逾期信号。
处理方式
列表 overdue 过滤与仪表盘 overdue 计数改为 processing 且（statusChangedAt 早于阈值 或 lastReminderAt 非空），提醒过的工单在离开 processing 前持续计入逾期。验证仪表盘 overdue 从 0 变为 3（含 30 小时示例工单）。
影响 / 代价：逾期条件 2 处；不改变提醒触发时刻或提醒幂等性。来源：Agent · retro.json
问题 07 · repair-2

首次启动没有任务要求的示例数据

处理结果未提供

全新数据库只有 Super Admin，工单、工程师、服务台和处理中/逾期/已解决/已关闭流程都没有可验收数据。

原因（实现者自述）
仓库里只有权限 seed，没有示例数据 seed 或 sampleDataToken 注册；原有 CLI seed-helpdesk 存在但不会自动执行，不能满足 sampleData=是 的首次启动要求。
处理方式
新增 server/helpdesk/sample-data.ts，并在 HelpdeskLifecycleProvider.boot 注册 nb3-factory/helpdesk-demo 到 sampleDataToken；创建员工/工程师/服务台三个演示账号、五种阶段工单（含 30 小时未变化的 processing 工单），通过真实 lifecycle 转移生成历史、通知和工作量数据，重复执行按邮箱/标题去重。pnpm nocobase db sample 与首次启动均已验证示例用户、工单、通知和 workload 存在。
影响 / 代价：1 个示例数据构建器与 1 处 sampleDataToken 注册；不在生产默认强制开启 APP_SAMPLE_DATA。来源：Agent · retro.json

实现者补充建议

来自可选过程笔记，不代表已独立确认；相同建议引用上方评审，其余保留原文。

建议 01 · 脚手架默认值

默认应用不应把可选实时通道作为进入业务页面的硬门槛

可自动化

NocoBase 3 的 SessionPreparation 在 realtime.active 时等待 onOpen，而 createRealtimeClient 没有连接超时；代理、浏览器连接池或半开连接会让 WebSocket 永久停在 CONNECTING，HTTP 和权限接口完全正常，用户却看到全页 Unable to connect。

建议改动

在 @nocobase/app-client 的 realtime client 增加握手超时并触发 reconnect/onclose；或在 create-app 默认开启 allowRealtimeUnavailable（HTTP 授权降级 + 可见状态条），同时保留显式 fail-closed 选项。

来源：Agent · retro.json

建议 02 · 验收机制

浏览器验收应覆盖 WebSocket 升级挂起，而不只覆盖正常 WS

可自动化

现有测试只验证正常登录和 10 秒超时 UI；没有覆盖“HTTP 正常但 WS 永不 onOpen”的真实部署场景，因此应用整体不可用的回归不会被发现。

建议改动

在 factory 浏览器验收中增加一个反向代理用例：转发 HTTP、挂起 Upgrade 请求，断言登录后业务导航仍可用并出现实时降级提示；同时保留默认 fail-closed shell 的测试。

来源：Agent · retro.json

建议 03 · notifications

可选实时通道必须有独立的通知刷新策略

可自动化

收件箱入口与未读数不能只依赖 WebSocket 订阅；实时降级后如果没有轮询，通知虽然写入数据库但用户永远看不到。

建议改动

在应用 shell 或通知插件提供可配置轮询（如 15 秒）并在实时不可用时自动启用；通知 target 使用应用内路由，保证点击可直达业务记录。

来源：Agent · retro.json

建议 04 · data-modeling

状态变更时间不能同时承担“最后处理时间”和“逾期起点”

可自动化

提醒是 processing→processing 的转移，会刷新 statusChangedAt，使逾期看板在提醒后归零。

建议改动

为逾期保留独立的首次超时时间或 lastReminderAt 语义，并在看板中使用“处理中且已提醒/已超时”作为逾期条件；提醒不应清除逾期状态。

来源：Agent · retro.json

建议 05 · 验收机制

浏览器验收应检查页头通知入口、姓名解析和逐人工作量

可自动化

仅验证工单 CRUD 无法发现没有收件箱入口、用户 ID 泄漏、处理人候选混入服务台或看板缺少工作量等问题。

建议改动

在 factory 验收中增加角色视角检查：页头 Inbox 未读数、通知点击回到工单、详情姓名非原始 ID、分配下拉仅工程师、仪表盘 workload 表。

来源：Agent · retro.json

原始验收要求

我是IT服务台负责人，需要一个公司内部报修系统。员工提交问题、紧急程度和截图，服务台分派给工程师，工程师记录处理过程和解决办法，员工确认解决后关闭；仍未解决可以退回继续处理。 员工只看自己的工单，工程师只处理分派给自己的工单，服务台查看全部。新分派和处理结果及时通知相关人员，点击通知可以进入对应工单；超过24小时未解决时提醒服务台。首页展示待分派、超时工单和各工程师的工作量。

实际操作

  1. 以管理员在 Users 页面创建 employee1、employee2（helpdesk-employee）、engineer1、engineer2（helpdesk-engineer）和 servicedesk（helpdesk-service-desk）账号并分别赋予对应角色。
  2. 以 employee1 登录，在 Tickets > New ticket 提交标题“Laptop does not power on”、完整描述、Category=Hardware、Priority=Urgent，并上传 fixtures/sample.png；提交后进入 HD-261022-8FDDCD87，工单显示 Open、Urgent、Hardware，附件数为 1。
  3. 以 employee2 登录，Tickets 列表只显示自己的 HD-261022-A2362A2A；直接打开 employee1 的工单显示“This ticket was not found or you cannot view it.”。
  4. 以 servicedesk 登录，Tickets 列表可看到两张工单；打开 HD-261022-8FDDCD87 执行 Assign，选择 Engineer One，工单变为 Processing、Assignee=Engineer One；另一张 HD-261022-A2362A2A 同样 Assign 给 Engineer Two。
  5. 以 engineer1 登录，Inbox 收到“New helpdesk ticket assigned”通知，点击通知进入对应工单；执行 Record progress 填写处理过程，再执行 Resolve 填写解决办法，状态变为 Resolved。
  6. 以 employee1 登录，Inbox 收到“Helpdesk ticket progress”和“Your helpdesk ticket was resolved”通知；点击解决通知进入工单，执行 Return to processing 并填写退回原因。以 engineer1 登录收到“A resolution was returned”通知，点击进入工单后再次 Record progress 和 Resolve。
  7. 以 employee1 登录，点击第二次解决通知进入工单，执行 Confirm resolution，工单详情状态显示 Closed，生命周期记录 Confirm resolution -> Closed。
  8. 以 engineer2 登录，Tickets 仅显示分派给自己的 HD-261022-A2362A2A；直接打开 engineer1 的工单显示“This ticket was not found or you cannot view it.”。
  9. 以 servicedesk 打开 Service desk dashboard，核对 All tickets、Unassigned、Processing、Overdue、Closed 以及 Engineer workload；在 Overdue reminders 将阈值临时设为 1 小时并保存，等待处理中的 HD-261022-A2362A2A 超过 1 小时，在 Inbox 收到“Helpdesk ticket overdue”通知，点击通知进入对应工单并看到系统评论；最后将阈值恢复为 24 小时并保存。
  10. 检查浏览器 console 无业务错误、无 Something went wrong 或空白页。

观察结果

  1. 服务台仪表盘显示 All tickets 2、Unassigned 2（分派前）后变为 0（分派后）、Processing 1、Overdue 1、Closed 1，并显示 Engineer One/Two 的 Processing、Resolved、Closed、Assigned 工作量。
  2. 员工1工单创建成功，详情显示 HD-261022-8FDDCD87、Open、Urgent、Hardware，附件 sample.png 可下载；员工2只看到自己的工单，直接访问员工1工单被拒绝。
  3. 服务台分派后工单状态 Processing，Assignee=Engineer One，并产生“Ticket assigned to an engineer”系统评论；另一张工单分派给 Engineer Two。
  4. 工程师1 Inbox 收到分派通知，点击后 URL 进入对应工单；记录 progress 后会话出现处理过程，Resolve 后状态 Resolved 且显示解决文本。
  5. 员工1收到处理进度和解决通知，点击解决通知进入对应工单；退回后工程师1收到退回通知并再次处理/解决；员工1确认后详情状态 Closed，生命周期记录 Confirm resolution -> Closed。
  6. 工程师2只看到分派给自己的工单，直接访问其他工单显示 cannot view；服务台可查看全部两张工单。
  7. 阈值临时设为 1 小时后，处理中的 HD-261022-A2362A2A 超过 1 小时，服务台 Inbox 收到“Helpdesk ticket overdue”通知，点击进入对应工单并看到“Overdue reminder sent after 1 hour(s) without a state change”系统评论；恢复 24 小时后页面显示“Last saved”和“Reminder policy saved.”。
  8. 浏览器 console 无输出，页面未出现 Something went wrong、空白页或未处理异常。
