问题 1

notification:test send 未登记为可授予资源，非 root 操作者无法经设置界面授权
NocoBase3 插件评审者判断 · 有证据轻微未解决
⌄

测试发送校验 resource {type:'notification', id:'test'}, action 'send'，而 notification 插件只在 authorization.resourceTypes.add 注册自定义授权器、未调用 authz.resources.add。权限设置界面的资源选项来自 authz.resources.definitionsList()，因此该资源/动作不会出现在界面中，管理员无法通过标准设置界面把它授予某个权限集合；当前只有 root 超管旁路或手工构造 API 授权才能通过。

实际影响 / 提供的帮助
对非超管操作者，测试发送实际不可用或需要非受支持的旁路；若未来要求由普通运维账号执行测试，会成为阻断点。当前浏览器检查使用初始管理员，故不影响本轮主流程。
建议改法 / 应保留的能力
在 notification 插件中为测试发送注册一个带 actions/grants 描述的资源（或资源组），使权限设置界面可选；或在 Skill/README 中给出明确的授权 API 步骤与最小权限示例。

改进建议 1

内置 Provider 无通用 HTTP 接收端，隔离接收需自定义 Provider
NocoBase3 插件评审者判断 · 有证据信息未解决
⌄

内置 Provider 仅覆盖 email（smtp/resend）与 IM（feishu-webhook/dingtalk-webhook），且后两者限定官方 HTTPS 主机。要让测试通知投递到本地隔离接收端，只能按扩展文档自行实现一个 Provider（本轮应用即写了 test-webhook）。这属于扩展机制的正常使用，而非能力缺失。
