本轮过程记录

Repaired the four failed service-desk criteria. B03: the return action now sends a submitted ticket back to the engineer (status processing, action returned) instead of the dead-end rejected state, only the supervisor can close/return, and a closed ticket is read-only for both attachments and lifecycle actions. B04: a temporarily shared ticket and an observer view are read-only, observer reads hide internal notes, and a confidential ticket is limited to the supervisor and its assignee (shares never open it). B06: attachment bytes are gated by ticket visibility (integrator denied), a corrupt image now shows explicit failure feedback with a download fallback, and removing an attachment removes the correct link. B07: the durable in-app message center is a real production page with navigation. Verified against the production build in a real browser plus the server self-tests.

问题 01 ·

Return dead-ends the ticket and engineers can close; closed tickets still accept attachments

处理结果未提供

Returning a submitted ticket moved it to rejected with no way back (b03-returned-to-engineer.png); an engineer saw the supervisor-only Confirm/close/Return actions (b03-engineerA-can-close.png); a closed ticket still offered attachment upload (b03-closed-upload-allowed.png, b03-closed-ticket2-upload-allowed.png).

原因（实现者自述）
TicketService.reject() set status='rejected' instead of returning the ticket to processing; engineer capability closeTickets was true, so the UI exposed the confirmation actions to the assignee; linkFile/unlinkFile did not check the ticket status, and the page gated the uploader only on canOperate/status in a way that left the closed case editable.

问题 02 ·

Shared and observer views were writable, internal notes leaked, confidential tickets unsupported

处理结果未提供

Engineer B saw Add files on a ticket shared to them (b04-engineerB-shared-ticket5.png); the observer list likewise exposed write affordances (b04-observer-tickets-list.png); internal resolution/rejection notes were visible to observers; there was no way to mark a ticket confidential.

原因（实现者自述）
The detail page gated the attachment editor on view/operate too loosely, TicketService.get() returned internal note fields and log detail to any viewer, and the repair ticket model had no confidentiality concept, so canView/canShare/canOperate could not restrict it.

问题 03 ·

Attachment bytes not access-controlled, corrupt image had no failure feedback, remove did not work

处理结果未提供

The integrator could download a ticket attachment (b06-integrator-attachment-access.png); a corrupt PNG rendered as a broken image without an explicit failure message (b06-corrupt-preview.png); Remove on an attachment did nothing (b06-remove-attempt.png).

原因（实现者自述）
The File plugin's generated content route was public, so any caller (or none) could fetch bytes; the image previewer had no onError fallback; FileList used FileRecord.key for the delete link id, but ticket-detail.tsx set key to the file UUID instead of the ticketFiles link id.

原因（实现者自述）
The notification-in-app plugin contributes its inbox only under a development-only route; the application had no production page, route or navigation entry for it.

建议 02 ·

DOCX preview could not be reproduced as broken

需人工判断

The B06 evidence showed the DOCX preview stuck on Loading, but the same sample.docx renders to a canvas in roughly 3.7s in both the dev server and the production build (the only image-path change was the corrupt-image fallback). The two QA screenshots b06-docx-preview.png and b06-docx-preview-loaded.png are byte-identical, which points at a capture/readiness artifact rather than a render failure; a criterion that waits for rendered output should allow for the wasm-backed first paint instead of screenshotting before it completes.
