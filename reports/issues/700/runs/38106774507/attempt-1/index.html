DefaultNamingStrategy 默认 underscored=true，fieldToColumnName 经 snakeCase 归一，关系外键追加 _id。

import { snakeCase, truncateIdentifier } from './utils.js';
export class DefaultNamingStrategy {
    options;
    constructor(options = {}) {
        this.options = {
            underscored: options.underscored ?? true,
            tablePrefix: options.tablePrefix ?? '',
        };
    }
    collectionToTableName(collectionName) {
        return `${this.options.tablePrefix}${this.normalize(collectionName)}`;
    }
    fieldToColumnName(fieldName) {
        return this.normalize(fieldName);
    }
    relationForeignKey(fieldName) {
        return `${this.normalize(fieldName)}_id`;
    }
    indexName(tableName, columns) {
        return truncateIdentifier(`idx_${tableName}_${columns.join('_')}`);
    }
    foreignKeyName(tableName, columns, targetTable) {
        return truncateIdentifier(`fk_${tableName}_${columns.join('_')}_${targetTable}`);
    }
    normalize(value) {
        return this.options.underscored ? snakeCase(value) : value;
    }
}

## What each API names

| API                                     | Names                              |
| --------------------------------------- | ---------------------------------- |
| `db.connection(name)`                   | a connection configuration name    |
| Builder collection, field, relation API | logical names                      |
| `query` table and column arguments      | connection-level query identifiers |
| `collections.get()` / `getPhysical()`   | Collection logical names           |
| `schemaInspector`                       | physical schema and table identity |
| `collectionMetadata`                    | Collection and field logical names |

Branch on `connection.dialect` (for example `'postgres'`) to detect the database; read `connection.driver` only for genuinely driver-specific code. `connection.client()` returns the underlying Knex instance and bypasses the schema guard, so it is the last resort and never a way around `'external'` — check `connection.capabilities` first.

## API shapes that do not exist

| Do not write                   | Write instead                       |
| ------------------------------ | ----------------------------------- |
| `db.builder`                   | `db.builder()`                      |
| `connection.builder()`         | `connection.builder`                |
| `db.query`                     | `db.query()`                        |
| `connection.query()`           | `connection.query`                  |
| `db.repository()` with no name | `db.repository('orders')`           |
| `connection.metadataStore`     | `connection.collectionMetadata`     |
| `connection.client`            | `await connection.client()`         |
| `connection.driver === 'pg'`   | `connection.dialect === 'postgres'` |

Do not generate `findUnique`, `findFirst`, `connectOrCreate`, `countDistinct`, `distinctOn`, native array fields, or a root-level `relations` argument. They are not part of this package, whatever a Prisma-shaped intuition or an old design proposal suggests.

export function defineSchedule(definition) {
    if (!definition.key || !/^[A-Za-z0-9][A-Za-z0-9._:-]*$/.test(definition.key))
        throw new Error('Schedule key must be a stable identifier.');
    if (!definition.title)
        throw new Error('Schedule title is required.');
    const parts = definition.schedule?.cron?.trim().split(/\s+/) ?? [];
    if (parts.length !== 5 && parts.length !== 6)
        throw new Error('Schedule cron must contain five or six fields.');
    const timezone = definition.schedule.timezone ?? 'UTC';
    try {
        CronExpressionParser.parse(definition.schedule.cron, {
            currentDate: new Date('2020-01-01T00:00:00.000Z'),
            tz: timezone,
        });
    }
    catch {
        throw new Error('Schedule cron or timezone is invalid.');
    }
    if (!definition.target?.type)
        throw new Error('Schedule target type is required.');
    assertNoSensitiveConfig(definition.target.config);
    if (definition.schedule.limit !== undefined &&
        (!Number.isInteger(definition.schedule.limit) ||
            definition.schedule.limit < 1))
        throw new Error('Schedule limit must be a positive integer.');
    if (definition.schedule.from &&
        definition.schedule.to &&
        definition.schedule.from > definition.schedule.to)
        throw new Error('Schedule from must not be after to.');
    const normalized = {
        ...definition,
        schedule: {
            ...definition.schedule,
            cron: definition.schedule.cron.trim(),
            timezone,
        },
    };
    const canonical = stableStringify(normalized);
    return freezeDeep({
        ...normalized,
        definitionHash: createHash('sha256').update(canonical).digest('hex'),
    });
}

        if (event.name !== 'ScheduleStart') {
            await this.updateDefinition(event.jobName, { nextRunAt });
            return;
        }
        for (let attempt = 0; attempt < RUN_COUNT_ATTEMPTS; attempt += 1) {
            const row = await this.database
                .query()
                .selectFrom('schedule_definitions')
                .select(['runCount', 'lastOccurrenceId'])
                .where('id', '=', event.jobName)
                .where('appName', '=', this.appName)
                .executeTakeFirst();
            if (!row || row.lastOccurrenceId === event.jobId)
                return;
            const runCount = Number(row.runCount ?? 0);
            const updated = await this.database
                .query()
                .updateTable('schedule_definitions')
                .set({
                runCount: runCount + 1,
                lastRunAt: event.runAt,
                nextRunAt,
                lastOccurrenceId: event.jobId,
                updatedAt: this.now(),
            })

                .where('appName', '=', this.appName)
                .where('runCount', '=', runCount)
                .where((eb) => eb.or([
                eb('lastOccurrenceId', 'is', null),
                eb('lastOccurrenceId', '<>', event.jobId),

                .execute();

async function dispatch(spec, context, { targets, occurrences }) {
    // The occurrence is the firing: its id is the executor's job id, so the same
    // firing delivered twice records, and starts its target, once.
    const occurrenceId = context.jobId;
    const executionContext = { scheduleId: spec.id, occurrenceId };
    const record = {
        scheduleId: spec.id,
        definitionHash: spec.definitionHash,
        targetType: spec.target.type,
        scheduledAt: context.scheduledAt,
    };
    const targetState = (await targets.describe(spec.target.type, spec.target.config)).state;
    if (targetState && targetState !== 'ready') {
        await occurrences.skip(occurrenceId, `target-${targetState}`, record);
        return;
    }
    const action = await occurrences.start(executionContext, spec.definitionHash, spec.target.type, context.scheduledAt);
    if (action === 'noop')
        return;
    try {
        const result = await targets.start(spec.target.type, spec.target.config, executionContext);
        switch (result.state) {
            case 'completed':
                await occurrences.succeed(occurrenceId, result.result);
                return;
            case 'accepted': {
                await occurrences.wait(occurrenceId, result.reference, result.receipt);
                const observation = await targets.inspect(spec.target.type, result.reference);
                if (observation.state === 'completed')
                    await occurrences.complete(occurrenceId, result.reference, observation.completion);
                return;
            }
            case 'skipped':
                await occurrences.skip(occurrenceId, result.reason);
                return;
            case 'failed':
                await occurrences.fail(occurrenceId, result.reason);
                return;
        }
    }
    catch (error) {
        try {
            await occurrences.fail(occurrenceId, 'dispatch-failed');
        }
        catch (completionError) {
            console.error('Failed to record schedule dispatch failure', {
                occurrenceId,
                error: completionError,
            });
        }
        throw error;
    }
}

## Decide Whether to Use Scheduler

The primary reason to define tasks through Scheduler is **UI observability for business administrators**. Developers define schedules and execution logic in code. Business administrators use the task list and detail pages the application builds on the Scheduler API to view schedules, track individual executions, and enable or disable tasks when authorized.

Tasks that do not need to be viewed and tracked through the UI must not be managed by the Scheduler plugin. Give recurring ones a `ScheduleExecutor` of their own from the application's jobs service (`jobExecutorServiceToken` in `@nocobase/app-server/jobs`), and one-off background work a `JobExecutor`; the application development Skill describes both. | Scenario                                                                                  | Choice          | Implementation boundary                                                                                  |

API error messages, notifications and mail need translation too. - Outbound content follows its recipient: mail, notifications and background work translate into the recipient's language, not the language of whoever triggered the work. A background job has no request to inherit a language from — resolve the recipient's locale explicitly and load it before translating. The `nocobase-app-plugin-i18n` Skill shows how server code translates, inside a request with `getRequestTranslator`, as an `AppI18nError` that the router's `onError` turns into an `ApiError` with a `localizedMessage`, and outside one with `getFixedT(namespace, locale)`.
- The frontend does not display an endpoint's `message` as is; it maps the status and the error's `reason` to its own copy (see [calling endpoints](frontend/references/api.md)).

## Keeping the server in step with the browser

`@nocobase/app-plugin-i18n` owns the language selector, persistence, and the server locale endpoints. The application shell calls `useSyncServerLocale()` so server messages use the browser's language when the server supports it; keep that call when changing the shell. If the server does not have that locale, the browser still switches and the server uses English; the language control shows an informational notice about the fallback.

## Which languages the application offers

The application's own locale files are the list. `client/locales/index.ts` decides what the browser offers and `server/locales/index.ts` what the server does, so adding a language means adding its file and loader entry on the side that needs it — there is no configured list to keep in step.

To add a language to the server, add its file annotated with `AppServerResource` (for example `server/locales/ja-JP.ts`) and its loader entry in `server/locales/index.ts`; the client side is described in [frontend copy and translations](frontend/references/i18n.md).

A plugin's locale file supplies translations for those languages, never a new one. A plugin shipping `ja-JP` to an application that does not offer Japanese puts nothing in the picker. Prefer keeping the client and server lists aligned when server-produced text needs the language. A client-only language is also valid: the interface switches to it, `PUT /api/i18n/locale` records English for the server, and the language control explains the fallback with an informational notice.

## Default language

`i18n.defaultLocale` in `config.yml` names the language the application starts in, for the browser and the server alike:

```yaml
i18n:
  defaultLocale: zh-CN
```

It defaults to `en-US`, and `APP_DEFAULT_LOCALE` overrides it. A value the application does not translate is ignored on the client and falls back on every key on the server.

The browser resolves its startup language as: the visitor's saved choice in `localStorage` → `i18n.defaultLocale` → `en-US`. The browser's own `navigator.language` is deliberately not consulted — the language an application starts in is the product's decision, not the visitor's operating system's. A default is never written to storage as though the visitor had chosen it, so changing configuration still reaches anyone who has not picked a language. Refresh after changing it.

Switching language in the interface remains a user-level choice: it writes `localStorage` and the server session, and never changes `defaultLocale`.
