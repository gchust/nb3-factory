This round repaired the realtime entry path: the application now states its WebSocket endpoint instead of deriving it from the API URL, and the session-preparation boundary releases when a socket for the current session opens after the preparation timeout, so a missed open notification can no longer leave a working application behind an "Unable to connect" screen that Retry cannot clear. This round also proved the earlier "Unable to connect" report: the verification browser's domain containment replaces WebSocket with a wrapper that drops its static readyState constants, which made the realtime client believe it was connected and never dial; the client now restores those constants before startup.

实现者补充建议

来自可选过程笔记，不代表已独立确认；相同建议引用上方评审，其余保留原文。

建议 01 · 验收机制

Poll durable inbox delivery in integration tests

可自动化

NotificationService.send persists before asynchronous channel dispatch completes. A single inbox read directly after a transition can race that dispatch.

建议改动

Use a bounded poll of the real inbox endpoint when asserting user-visible notifications, as the ticket workflow test now does.

来源：Agent · retro.json

建议 02 · 验收机制

Cover the session-preparation boundary with an open that arrives after the timeout

可自动化

The barrier was only tested for ready, timeout and retry. The failure mode that blocked users was an open notification delivered after the provider unsubscribed, which no test produced.

建议改动

When touching an authentication or realtime gate, add a case that delivers the success notification after the gate's own timeout and asserts the gate releases.

来源：Agent · retro.json

建议 03 · configuration

State derived client URLs explicitly in configuration tests

可自动化

api.realtimeURL was derived from api.baseURL through a `..` segment; the derivation worked only because the browser normalizes the path, so a proxy or CDN could break the handshake silently.

建议改动

Assert every derived-but-critical client URL (API, realtime, uploads) in a config test, and prefer stating it in client/config.

来源：Agent · retro.json

建议 04 · 验收机制

Exercise the client under browser instrumentation that wraps platform constructors

可自动化

A plain browser cannot see that containment wrappers may replace WebSocket without its static readyState constants, which made the application fail only in the verification browser.

建议改动

When verification wraps globals (allowed domains, init scripts, proxies), rerun the acceptance path through a test that stubs the wrapper, and treat missing static constants on any replaced constructor as expected environment behavior the application normalizes once at startup.

来源：Agent · retro.json

原始验收要求

我是IT服务台负责人，需要一个公司内部报修系统。员工提交问题、紧急程度和截图，服务台分派给工程师，工程师记录处理过程和解决办法，员工确认解决后关闭；仍未解决可以退回继续处理。 员工只看自己的工单，工程师只处理分派给自己的工单，服务台查看全部。新分派和处理结果及时通知相关人员，点击通知可以进入对应工单；超过24小时未解决时提醒服务台。首页展示待分派、超时工单和各工程师的工作量。

实际操作

  1. 管理员创建 tickets-requester、tickets-maintainer、tickets-admin 测试账号，分别登录并完整重新加载业务页面。
  2. 员工 QA Employee 提交工单：标题、描述、Priority=High、截图 sample.png，生成 TKT-MVHFGLEH-9DEA26，附件 sample.png（99 B）可见。
  3. 服务台 QA Desk 登录后看到全部工单，将 VPN 工单分派给 QA Engineer，状态变为 In progress；另将 QA Desk 提交的打印机工单分派给 QA Engineer Two。
  4. 工程师 QA Engineer 登录后列表仅出现分派给自己的 VPN 工单；直接打开他人打印机工单 URL 显示“This ticket does not exist or you cannot see it.”；在工单中回复处理过程并附 sample.pdf，再回复解决办法并 Resolve。
  5. 员工收到分派、处理结果、已解决通知；从通知详情标题链接进入对应工单；员工执行 Reopen 退回，工单回到 In progress；工程师再次回复并 Resolve；员工执行 Confirm resolution，工单变为 Closed。
  6. 服务台首页核对 Active tickets、Unassigned、Overdue、Engineer workload 与 Recent tickets；工程师/员工首页核对各自可见工单范围。
  7. 员工尝试上传 corrupt.png 和 unsupported.exe 作为截图/附件，并提交含 unsupported.exe 的工单；服务台打开分派下拉核对候选工程师。

观察结果

  1. 正常流程可完成：员工建单（High、sample.png）、服务台分派、工程师回复处理过程+解决办法并 Resolve、员工 Reopen 退回、工程师二次处理、员工 Confirm resolution 关闭，状态依次为 Open→In progress→Awaiting confirmation→In progress→Awaiting confirmation→Closed。
  2. 角色隔离有效：员工列表仅见自己的工单；工程师列表仅见分派给自己的工单，直接打开他人工单 URL 被拒绝；服务台列表可见全部 3 张工单。
  3. 通知有效：工程师收到分派/退回通知，员工收到处理结果/已解决通知，服务台收到新工单/关闭通知；通知详情中的标题链接可进入对应工单（点击通知条目本身先打开通知详情）。
  4. 首页统计有效：服务台首页显示待分派、超时区块、工程师工作量（QA Engineer 1 active、QA Engineer Two 1 active）并随操作变化；员工首页显示自己的待确认工单。
  5. 附件校验缺陷：corrupt.png 与 unsupported.exe 均被 Screenshot/附件控件接受且无任何错误提示；unsupported.exe 还成功创建工单 TKT-MVHFOOL0-A17ECE 并作为附件展示，corrupt.png 也可追加到该工单。与清单预期的“明确失败/不支持格式反馈”不符。
  6. 超时提醒未能在本轮触发：页面存在 Overdue/Past the 24-hour target 区块和工单 24-hour target 字段，但无法在单次会话内等待 24 小时，未观察到超时提醒通知。
  7. 旁证：工程师首页仍使用报修人视角文案（Follow your requests / My open requests），并把他人提交、分派给自己的工单列在“My open requests”下；分派候选人下拉包含非工程师账号 QA Desk。
