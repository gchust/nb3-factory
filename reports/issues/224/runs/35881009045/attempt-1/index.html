Problems & resolutions

遇到的问题

用迁移 + 幂等种子 + 应用自有 Hono 路由 + 应用自有页面实现了 Customers/Contacts/Opportunities 三实体 CRM，登录即访问边界，附带真实 SQLite 的 migration/seed/service/route 测试与表单组件测试。修复轮将所有 overlay 新增/编辑页面的 useRouteOverlay 调用从渲染 RouteDialog 的页面组件移入其内部后代组件，并补充六个 overlay 页面的渲染回归测试。

问题 01 · 实现阶段

datetime 字段不接受带 Z 的 ISO 字符串

处理结果未提供

种子/服务写入 createdAt 时抛出 RepositoryError: Invalid datetime value for Field "createdAt". Expected a valid V1 temporal value with at most millisecond precision.

原因
NocoBase datetime 是 naive V1 时间值，normalizeTemporalValue 明确拒绝带时区后缀的字符串；固定种子时间写成了 new Date().toISOString() 形式。
处理方式
种子固定时间改为 '2026-01-01T00:00:00.000'（无 Z），运行时写入使用 new Date()（按本地 getter 转换），返回时统一重新读取数据库中的存储值。
影响 / 代价：约两轮调试：先在种子执行时暴露，后在客户详情页 total 断言时确认存储格式。来源：Agent · retro.json
问题 02 · 实现阶段

客户端没有 QueryClientProvider，react-query hooks 不可用

处理结果未提供

按常规写法引入 @tanstack/react-query 的 useQuery 后发现 @nocobase/app-client 的 dist 中没有任何 QueryClientProvider。

原因
模板的 app-client 不挂载 react-query 上下文，插件式用法与独立 App 不同。
处理方式
改为自建 useCrmData hook，内部用 ref + AbortController + 请求 identity 派生 loading，既满足 react-hooks set-state-in-effect 规则，也避免竞态。
影响 / 代价：约一轮实现返工。来源：Agent · retro.json
问题 03 · 自动验证

仓库基线 lint 在 .github 下为红色

处理结果未提供

pnpm lint 报 66 个错误，全部位于 .github/scripts 与 .github/reports 的 .mjs 文件（Buffer/structuredClone/setTimeout 等 no-undef）。

原因
工厂控制面脚本的 eslint 环境未声明 Node globals，属于模板基线的既有问题，与业务改动无关。
处理方式
未触碰 .github（受保护）。改为对新增/修改的应用文件单独运行 eslint 并确认 0 错误。
影响 / 代价：几乎没有额外成本，但需要在交付说明中显式澄清。来源：Agent · retro.json
问题 04 · 修复阶段

页面在渲染 RouteDialog 的同一组件中调用 useRouteOverlay

已解决

打开 Add customer / Add contact / Add opportunity 或任一 Edit 页面时，URL 跳转正确但主区域显示 'Unable to load page'，控制台抛 Error: useRouteOverlay must be used inside RouteDialog or RouteDrawer，新增/编辑表单全部不可用。

原因
RouteOverlayContext.Provider 位于 RouteOverlay（RouteDialog/RouteDrawer 的公共实现）内部；调用 useRouteOverlay() 的页面组件是 Provider 的父级。React context 只能由后代读取，因此拿到 null 并抛错。
处理方式
把取数、提交与关闭逻辑连同 useRouteOverlay 调用移入 RouteDialog 内部的后代组件（NewCustomerForm/EditCustomerForm 等），页面组件只保留标题与 <RouteDialog> 外壳。
影响 / 代价：约一轮定位加六个页面的机械式重构。来源：Agent · retro.json
Improvement opportunities

可改进的点

为什么值得改、具体改哪里，以及能否自动化；与已经发生的问题和修复结果分开记录。

建议 01 · Skill 与文档

在 database-and-data / migrations 参考中显式写明 datetime 是 naive 值、不得带 Z

可自动化

本次最大的一次返工来自 datetime 的 V1 语义：文档只说明字段类型，没有说明字符串输入必须省略时区后缀，而 new Date().toISOString() 恰恰是最自然的写法。

建议改动

在 migrations 与 database-and-data 参考的 datetime 小节加入一条显式规则与正反例：可写 new Date() 或 '2026-01-01T00:00:00.000'，不可写 '...Z'。

来源：Agent · retro.json

建议 02 · Skill 与文档

在 client-api / components 参考中说明模板不挂载 react-query

可自动化

应用页面的数据获取没有现成 query client，容易先写 react-query 再返工。

建议改动

在 client-api 参考中说明可用 useApiClient + 自建 hook（AbortController）取数，并给出最小示例。

来源：Agent · retro.json

建议 03 · 验收机制

工厂预检应区分应用源码 lint 与 .github 基线 lint

可自动化

pnpm lint 在干净仓库上就会因控制面脚本报 66 个 no-undef，agent 无法通过完整 lint，只能自证应用文件干净，容易造成误判。

建议改动

为 .github/scripts、.github/reports 提供独立的 eslint Node 环境配置（或在验收时对应用路径与 .github 路径分别判定），使应用侧 lint 结果可独立解读。

来源：Agent · retro.json

建议 04 · 验收机制

为 overlay 页面补充组件级渲染测试或静态检查

可自动化

useRouteOverlay 用错位置只有在浏览器点击进入页面时才暴露；route-overlay 单测只覆盖了正确用法的 Actions 组件，没有任何测试渲染 CRM 的新增/编辑页面组件，因此缺陷在应用测试阶段完全静默。

建议改动

模板给出 overlay 页面渲染测试模式（RouterProvider + mock useApiClient/i18n），断言表单出现且 Cancel 能关闭；或在 eslint 增加规则，检测返回 RouteDialog/RouteDrawer 的组件体内直接调用 useRouteOverlay。

来源：Agent · retro.json
