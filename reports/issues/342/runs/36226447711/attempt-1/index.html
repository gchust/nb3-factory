问题 01 · 实现阶段

种子文件 import 应用运行时常量导致 ERR_MODULE_NOT_FOUND

本任务已处理

把权限集矩阵放在 database/seed-data/*.ts 并被种子 import 后，db:apply 加载种子时报模块解析失败。

原因（实现者自述）
种子运行环境不解析应用源码别名，且种子必须是自包含的；跨文件 import 应用侧常量既违反自包含约束也会在打包后失效。
处理方式
删除 database/seed-data/，把页面授权矩阵直接内联进 database/main/seeds/202610100101_service_permission_sets.ts。
影响 / 代价：一次 db:apply 失败与一次返工。来源：Agent · retro.json
问题 02 · 实现阶段

api 贡献里 use('*') 吞掉全部 /api 路由（含未注册路径）

本任务已处理

server/routes/files.ts 用 router.use('*', auth.required()) 后，app-server 的 isolated 测试中任意 /api/* 都返回 401，预期 200 的用例失败。

原因（实现者自述）
框架把每个 api 贡献都挂在 /api（application 里 route('/api', router)），因此贡献内的 '*' 会匹配到所有 /api/*，包括其它贡献与应回退到 SPA 的未注册路径。
处理方式
改为从 exposure.actions 推导 '/<name>:<action>' 列表并逐个 use(path, auth.required())，root 贡献按 accessPath 前缀收窄。
影响 / 代价：未提供，不估算来源：Agent · retro.json
问题 03 · 实现阶段

本任务已处理

为收窄文件路由改用 router.use(/^\/serviceAttachments(:|$)/, ...) 触发 TS2769：Argument of type 'RegExp' is not assignable to parameter of type 'string'。

原因（实现者自述）

处理方式

问题 07 · 浏览器验收

权限集种子的 grants 全为空，业务岗位被判"无权限"且 API 500

本任务已处理

所有 service-* 权限集在 authorizationPermissionSets.grants 里是 "[]"，任何岗位打开业务页都是 No access；所有 /api/service/* 返回 500（内容为 "Not a service user." 的错误体），页面显示"Unable to load the data"。

原因（实现者自述）

处理方式
改为 let builder = defineJob(...) 并在循环内 builder = builder.grant(...) 累积；同时给 service-admin 增加 database-explorer 页面授权。新增 tests/logic/service-permission-sets.test.ts 钉住每个岗位的页面授权，防止回归。
影响 / 代价：一次全量验收失败 + 一轮根因排查与修复。来源：Agent · retro.json

文件插件的字节路由挂在应用根路径且只做登录校验；应用此前只在 api 贡献里按动作守卫资源 CRUD，未给根字节路由加记录级授权。
处理方式
新增 server/service/attachments.ts 的 assertCanReadAttachment：解析调用者岗位与页面权限，反查 workOrderAttachments 得到所属工单，套用与工单 API 相同的区域/机密/协作范围——无岗位或文件未链接工单 403，工单不可见 404（与工单 API 的存在性一致）。server/routes/files.ts 的根路由改为 Hono<AuthorizationEnv>，按 accessPath/:file 先 auth.required()+authorization.middleware() 再断言，并用 serviceErrorResponse 映射错误。新增 tests/logic/service-attachment-access.test.ts 覆盖授权/越权/无岗位/集成账号/未链接五种情形。
影响 / 代价：一个新服务模块 + 根路由改造 + 1 组测试。来源：Agent · retro.json

建议 01 · Skill 与文档

在 app-development Skill 明确 api 贡献禁止 use('*')

可自动化

server-routes.md 提到按路径限定中间件，但没有点明：因为每个 api 贡献都挂在 /api，一个 '*' 会连未注册路径和 SPA 回退一起吞掉，症状是无关用例 401。

建议改动

在 references/server-routes.md 增加反例与正例，并补充本仓库 Hono 版本 use() 只接受 string 路径（正则会 TS2769），给出从资源动作列表推导守卫路径的写法。

来源：Agent · retro.json

建议 02 · 工具与构建

为未知类型行值提供统一的 text/optionalText 工具

可自动化

db.query() 返回值是 unknown，严格 ESLint 下必须逐处收窄；每个应用都会重复踩这个坑。

建议改动

在 app-development 的 database-and-data.md 给出推荐工具片段，或在 @nocobase/db 提供导出的读取 helper。

来源：Agent · retro.json

建议 03 · 验收机制

区分基线 lint/format 失败与本次改动引入的失败

可自动化

全量 pnpm lint/format:check 在本模板 .github/ 上稳定失败，容易被误读为本次改动不合格；本次通过过滤非 .github 路径确认应用源码零问题。

建议改动

要么把 .github/ 纳入规则，要么在模板脚本里排除并在文档中说明；或在验证文档中给出按变更范围过滤的推荐命令。

来源：Agent · retro.json

建议 04 · Skill 与文档

在 app-development 文档中点明权限集 Builder 不可变

可自动化

种子用 defineJob(...).grant(...) 却丢弃返回值时，grants 会静默写为空数组，数据库看起来正常，唯一症状是所有岗位"无权限"并连带 API 500，排查成本很高。

建议改动

在 references/database-and-data.md 或新的权限种子小节明确：PermissionSetBuilder 的方法返回新实例，必须累积赋值；并给出对已写入 grants 的断言示例。

来源：Agent · retro.json

建议 05 · 工具与构建

为客户端 DTO 与服务端集合字段提供契约检查

可自动化

客户端表单字段名与服务端输入字段名漂移时，值被静默丢弃或未使用的字段直接 400；类型系统因为两侧各自声明而无法发现。

建议改动

在生成 collections 工件之后，增加一个可选的契约测试：从 collection metadata 推导字段名，校验客户端 api/types 中同名 DTO 的键；或在 app-development 文档给出该模式。

来源：Agent · retro.json

建议 06 · 验收机制

权限改动需要页面授权与 API 守卫的成对测试

可自动化

权限集种子坏了会同时表现为"页面无权限"和"API 500"；只测其中一侧会漏掉另一侧，而且 500 会掩盖后续的字段/校验缺陷。

建议改动

在 testing.md 建议：权限相关改动至少覆盖每个岗位的页面 grants 断言 + 一个越权/授权 API 用例（含非业务用户 403 而非 500）。

来源：Agent · retro.json

建议 07 · upstream-plugin

调度插件应渲染 occurrence 的业务结果

需人工判断

ScheduleOccurrenceStore 已保存 resultSummary，但插件的触发记录表只渲染 startedAt/duration/status/target，业务管理员看到的"执行结果"只有 triggered/succeeded，容易把"已触发"当成"业务已完成"。本次只能在应用目标上实现 describe() 把最近结果写进 targetSummary.description 绕过。

建议改动

在 @nocobase/app-plugin-scheduler 的触发记录/计划详情中展示 occurrence.resultSummary（以及失败时的 reason），或在文档中明确推荐用 target 的 describe() 暴露最近结果。

来源：Agent · retro.json

建议 08 · upstream-plugin

文件插件的根字节路由缺少记录级授权扩展点

需人工判断

FileRepositoryApiExposure 只能声明资源的 CRUD 动作与字段，根字节路由（accessPath/:file）只校验登录身份，不暴露任何按记录授权的钩子。应用只能在自己的根贡献里用相同路径前缀再包一层，并自行反查文件到业务记录的归属，逻辑重复且容易漏。

建议改动

为字节路由增加授权回调（如 authorizeRead(record, context)）或至少在文档中给出应用包一层的推荐写法与顺序。

来源：Agent · retro.json

建议 09 · Skill 与文档

在文件预览相关文档中点明 Content-Disposition 与可选 OOXML part

可自动化

两个反复出现的预览故障都不是应用逻辑错误：字节路由一律 attachment 会让 iframe 变 about:blank；最小 xlsx 缺少 ECMA-376 可选的 xl/styles.xml 会让 WASM 解析器拒绝加载。

建议改动

在 app-development 的 file/预览小节记录这两条：预览内联需要把可预览类型的 disposition 改写为 inline；对 xlsx 需要保证 xl/styles.xml 存在（或在查看器侧容错）。

来源：Agent · retro.json
