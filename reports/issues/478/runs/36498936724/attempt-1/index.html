问题 01 · 实现阶段

Application provider crashed in minimal and pre-migration runtimes

本任务已处理

tests/logic/app-server.test.ts failed three cases: `Service "@nocobase/app/authorization" is not registered` in one, and `RepositoryError: Collection "serviceCustomers" does not exist` in two.

原因（实现者自述）
ServiceApplicationProvider.boot() unconditionally resolved the optional authorization and user-administration tokens, and ServiceBootstrap.run() wrote sample data without checking that the application's own migration had created the service tables. A minimal test runtime registers neither plugin, and an embedded app whose database directory has no application migrations has no service tables.
处理方式
boot() now only runs the bootstrap when both optional tokens are present in the container, and ServiceBootstrap.run() checks `db.builder().hasCollection('serviceCustomers')` before the sample-data phase (accounts and roles are still provisioned). All 44 test files / 331 tests pass.
影响 / 代价：未提供，不估算来源：Agent · retro.json
问题 02 · 实现阶段

Ticket keyword search raised a runtime repository error

本任务已处理

`RepositoryError: Filter group "string" does not match Field "description" of type "text"` when listing tickets with a keyword; live ticket search would return 500.

原因（实现者自述）
The ticket list filter used `filter.string('description').includes(...)` against a `text` column. Filter groups are typed by declared field type and the mismatch only fails at execution time.
处理方式
Switched to `filter.text('description').includes(keyword, { mode: 'insensitive' })` and added the matching `text(path)` method to the hand-written filter type stub. Covered by tests/logic/service-business.test.ts.
影响 / 代价：未提供，不估算来源：Agent · retro.json
问题 03 · 实现阶段

Workflow auto-enable has no public API

本任务已处理

The acceptance Workflow package loads but is disabled; there is no exported WorkflowRepository, no `enable` CLI command, and no auto-enable config, so a normal trigger would not run.

原因（实现者自述）
Enablement state is stored in the workflow plugin's own tables and the plugin exposes no public contract for source-managed packages to declare themselves enabled.
处理方式
The accept endpoint triggers the workflow with `{ manually: true, waitForCompletion: true }` and falls back to the idempotent service-level `acceptTicket` if no run is produced. Acceptance stays idempotent (one state change, one notification) whichever path executes.
影响 / 代价：未提供，不估算来源：Agent · retro.json
问题 04 · verification

Acceptance Workflow run nodes failed at runtime

本任务已处理

The accept endpoint produced a Workflow run, but every run node logged `Instruction "run" failed`: `Cannot find module .../server/accept.js` in development, and `Cannot find module .../workflows/services/contracts.js` from the materialized production Artifact. The failed run recorded no business effect and QA found 0 successful runs.

原因（实现者自述）
Two independent causes. (1) Run modules imported siblings with `.js` specifiers, which Node native TypeScript stripping does not map back to `.ts` in development. (2) The production Workflow Artifact is a self-contained copy under `storage/workflows/<key>/<digest>`; relative imports escape the copy root, and `ServiceContainer` matches bindings by token object identity, so a copy of `contracts.js` would also create a second token the application container never registered.
处理方式
Run modules import siblings with `.ts` specifiers (rewritten to `.js` by `rewriteRelativeImportExtensions` for the Artifact) and read application service tokens from a process-wide `globalThis` registry (`Symbol.for("nb3-factory.service-token-registry")`). The application creates each token once in `server/services/service-token.ts`; the workflow-local `server/workflows/ticket-acceptance/server/service-tokens.ts` returns the identical object. Verified in development (Node loading the `.ts` source) and against the compiled Artifact copied outside `node_modules`: both run nodes execute and `summarizeAcceptance` records the resulting status.
影响 / 代价：未提供，不估算来源：Agent · retro.json
问题 05 · verification

Header notification bell broke the baseline shell layout test fixture

本任务已处理

Three tests in tests/components/layout-i18n.test.tsx failed with `TypeError: Cannot read properties of undefined (reading 'resolve')` from `useService` -> `useApiClient` -> `NotificationInAppProvider`.

原因（实现者自述）
The in-app notification bell was added to `HeaderActions`, which every shell layout renders. `NotificationInAppProvider` resolves `apiClientToken` and `realtimeClientToken` from `app.services`, but the layout-i18n test fixture built a partial `ClientApplication` with only `config` and `runtime`. tests/logic/client-shell.test.tsx had already been updated with those two tokens; this fixture was missed.
处理方式
Added a service map with `apiClientToken` and `realtimeClientToken` to the layout-i18n `setup()` fixture, matching client-shell.test.tsx, so the real bell keeps rendering while the shell translation assertions stay unchanged. Re-ran tests/components plus the client-shell and client-runtime logic tests: 18 files / 143 tests pass; prettier and eslint clean on the changed test file.
影响 / 代价：未提供，不估算来源：Agent · retro.json

建议 01 · api

Filter operator and field type mismatch is only caught at runtime

可自动化

Using a filter group that does not match a collection field's declared type compiles cleanly and throws RepositoryError at execution. This cost a live bug in ticket keyword search and is easy to repeat with text vs string columns.

建议改动

Derive the repository filter type from the declared collection metadata so `filter.text` / `filter.string` selection is checked by the compiler, or surface the mismatch as a startup/schema validation warning.

来源：Agent · retro.json

建议 02 · workflow

Workflow run scripts cannot share application modules or token instances

可自动化

A run script is loaded from a copied Artifact directory: relative imports escape the copy root, the copy is a separate module instance, and the Artifact may sit outside the server node_modules. `ServiceContainer` matches by token identity, so importing the application contracts module from a run script can never resolve a service even when the import loads. The failure only appears when the node first runs.

建议改动

Give the Workflow plugin a first-class way for an application-owned run script to receive application services (for example service instances in run options, or a documented global token-registry helper), and make the Workflow build reject a run module that imports outside its package root.

来源：Agent · retro.json

建议 03 · testing

Partial ClientApplication fixtures must track new shell service dependencies

可自动化

Shell components are rendered across several tests, and each test builds its own `ClientApplication` fixture. When HeaderActions gained a plugin provider that reads `app.services`, only the fixtures that already supplied services kept working; the layout-i18n fixture silently lacked a `services` field that TypeScript could not require because the object is cast `as unknown as ClientApplication`.

建议改动

Provide a shared test helper that builds a `ClientApplication` fixture with the standard tokens (`apiClientToken`, `realtimeClientToken`, authentication/authorization) defaulted, and have shell tests spread overrides onto it, so adding a service-backed header component updates every fixture in one place.

来源：Agent · retro.json
