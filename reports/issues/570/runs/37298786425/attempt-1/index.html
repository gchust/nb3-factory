问题 01 · 自动验证

it-tickets 服务与路由的 17 个 @typescript-eslint/no-unsafe-* 报错

本任务已处理

verify-2 的 lint 阶段退出 1：server/providers/it-tickets.ts 117/121/123/127/131/136 行与 server/routes/it-tickets.ts 36/40 行报 unsafe assignment/call/return/member-access/argument。

原因（实现者自述）
scoped 是 async 辅助函数，返回 Promise<RepositoryOperations<...>>，但代码直接在其上链式调用 findMany/findOne/createOne/updateOne，TS 把接收者解析为类型错误（any/error type）；createOne/updateOne 返回 SingleMutationResult<T>（含 .record），却按 Promise<T> 返回；authorizationToken 误从 @nocobase/app-plugin-authentication/server 导入而非 @nocobase/app-plugin-authorization/server；ItTicketsProvider.boot 声明为 void 而接口要求 Promise<void>。
处理方式
把 const view = await scoped(...) / const tickets = await scoped(...) 拆开后再调用；createOne/updateOne 解构 { record } 并 return record；authorizationToken 改从 authorization 包导入（authenticationToken/AuthEnv 仍来自 authentication 包）；boot 改为 async boot(): Promise<void>。
影响 / 代价：修改 server/providers/it-tickets.ts 与 server/routes/it-tickets.ts 两个文件。来源：Agent · retro.json
问题 02 · 自动验证

空插件组合下 ItTicketsProvider.boot 解析 authorizationToken 失败，app-server 测试挂掉

本任务已处理

lint 修好后首次运行 pnpm test，tests/logic/app-server.test.ts 报 "Service \"@nocobase/app/authorization\" is not registered."，307 个测试中 1 个失败。verify-2 在 lint 处已中止，所以该失败此前从未暴露。

原因（实现者自述）
tests/logic/app-server.test.ts 用 defineServerPlugins([]) + appRuntime.serviceProviders 组装内嵌应用，不加载 Authorization 插件；新增的 ItTicketsProvider.boot/路由工厂无条件 container.resolve(authorizationToken)，在缺少该插件的组合下抛错。
处理方式
沿用 app-plugin-users 的既有模式：provider boot 先 container.has(authorizationToken)，不存在则直接 return；路由工厂在 authenticationToken 或 authorizationToken 任一缺失时返回一个未挂载任何路由的空白 Hono，避免把工单端点以未鉴权形式挂出。生产组合两插件始终存在。
影响 / 代价：server/providers/it-tickets.ts 与 server/routes/it-tickets.ts 各加一处可用性守卫。来源：Agent · retro.json
问题 03 · 自动验证

生产 build 的 server 编译在 it-tickets 路由工厂报 TS2345（两种 Hono Env 的联合）

本任务已处理

lint 修好后运行 pnpm build：client 构建成功，server 编译报 server/routes/it-tickets.ts(33,3) TS2345，'(app) => Hono<BlankEnv> | Hono<AuthEnv & AuthorizationEnv>' 不能赋给 AppRouterFactory；而 pnpm typecheck（tsc -p tsconfig.server.json --noEmit）此前显示通过。

原因（实现者自述）
为修测试而加的守卫分支 return new Hono<AuthEnv & AuthorizationEnv>()，而工厂末尾 return router 是 new Hono()（Hono<BlankEnv>）；build 的 server 编译对 defineApiRoutes 回调返回类型比 tsconfig.server.json 更严格，明确要求两个返回分支 Env 一致。
处理方式
守卫分支改为 return new Hono()，与末尾返回的空白 router 同型，回调返回类型统一为 Hono<BlankEnv>。build 与 typecheck 均恢复通过。
影响 / 代价：server/routes/it-tickets.ts 一行类型修正。来源：Agent · retro.json

问题 05 · repair-3

员工创建工单返回 500：RepositoryError: Writing field "assigneeId" is not allowed

本任务已处理

重启开发服务器后以员工 linxiaoyu 调用 POST /main/api/tickets 返回 500，响应 code=TICKET_FAILED，服务端日志为 RepositoryError: Writing field "assigneeId" is not allowed （server/providers/it-tickets.ts 的 create 分支）。

原因（实现者自述）
create 的 values 里显式写入了 assigneeId/assigneeName/resolution/startedAt/completedAt 六个处理人所有的字段并置为 null，而 it-employee 的 create 授权只覆盖 title/category/description/status/createdById/createdByName/createdAt/updatedAt；写入策略对未授权字段直接拒绝，即使值为 null。
处理方式
从 create 的 values 中删除这六个字段，改为依赖 nullable 列自身默认 NULL；处理人字段仍在 start/complete 各自授权下写入。为保持最小授权，未扩大 create 的写策略。
影响 / 代价：server/providers/it-tickets.ts create 分支的 values 收敛为提交字段 + 状态 + 报修人 + 时间戳。来源：Agent · retro.json
问题 06 · repair-3

种子相对导入使 tests/logic/app-server.test.ts 启动应用失败（ERR_MODULE_NOT_FOUND）

本任务已处理

补齐客户端与种子后运行 pnpm exec vitest run tests/logic，27 个文件中 app-server.test.ts 两个用例失败：AppDatabaseTaskError: Database seeds failed ... Cannot find module '.../server/it-tickets.js' imported from .../database/main/seeds/202610010002_it_tickets_demo.ts；把该导入去掉后错误改为找不到 .../database/seed-data/permission-sets.js。pnpm nocobase db apply 用同一批导入却正常。

原因（实现者自述）
应用启动与 vitest 的 app-server 测试通过 @nocobase/db 的 importTaskDefinition 以原生 import() 加载 任务文件，Node 只做类型剥离并按字面 specifier 解析相对导入；'.js' 指向不存在的编译产物。而 CLI 的 db apply 用了另一套重映射加载器，所以只有测试路径暴露。
处理方式
把种子对 permission-sets 的相对导入写成 '.ts'：Node 24 原生类型剥离能解析，tsconfig.server.json 的 allowImportingTsExtensions + rewriteRelativeImportExtensions 让 pnpm build 产出 '.js' 导入，二者兼得；同时把 permission-sets.ts 内的授权字面量写成自包含（不再导入 server 的 composite 资源声明），既满足种子的自包含要求，又由 tests/logic/it-tickets-permissions.test.ts 与 server 声明对齐。
影响 / 代价：database/main/seeds/202610010002_it_tickets_demo.ts 一行导入后缀，database/seed-data/permission-sets.ts 改为字面量声明。来源：Agent · retro.json

实现者补充建议

来自可选过程笔记，不代表已独立确认；相同建议引用上方评审，其余保留原文。

建议 01 · 验收机制

pnpm typecheck 与生产 build 的 server 类型检查不一致，漏报 TS2345

可自动化

server/routes/it-tickets.ts 在 pnpm typecheck（tsc -p tsconfig.server.json --noEmit）下通过，但 pnpm build 的 server 编译因 defineApiRoutes 回调返回类型要求更严格而报 TS2345。修复一个 lint 失败后，下一个失败在 build 才出现，多消耗一轮修复。

建议改动

让 tsconfig.server.json 使用与生产 build 相同的 server 编译设置（或把 build 前的 server 类型检查纳入 typecheck 阶段），使 typecheck 能在提交前报出同类错误。

来源：Agent · retro.json

建议 02 · Skill 与文档

应用自有 ServiceProvider 依赖插件 token 时应先用 container.has 探测

需人工判断

内嵌 app-server 测试用空插件组合启动应用，任何在 boot/路由工厂里无条件 container.resolve(插件 token) 的 provider 都会让其失败。app-plugin-users 已采用 container.has 模式，但应用开发 Skill 未明确要求应用侧 provider 也这样做。

建议改动

在 nocobase-app-development 的 server-routes/services 参考中补充：应用 provider/路由在 resolve 插件 token 前先 container.has，并说明缺失时应跳过挂载而不是以未鉴权形式暴露端点。

来源：Agent · retro.json

建议 03 · Skill 与文档

数据库任务相对导入在原生 Node 加载路径下必须带 .ts 后缀

需人工判断

migration/seed 由 @nocobase/db 以原生 import() 加载（vitest app-server 测试、生产 dist），Node 类型剥离不重映射 '.js'→'.ts'，所以任务内引用其它应用源码时 '.js' 会 ERR_MODULE_NOT_FOUND；只有 CLI 的 db apply 用了重映射加载器所以本地看起来正常。

建议改动

在 nocobase-db 的 migrations/seeds 参考里写明：任务文件内部引用其它 .ts 源码时用 '.ts' 后缀，并说明 allowImportingTsExtensions + rewriteRelativeImportExtensions 会在构建时改写为 '.js'；更推荐任务保持自包含、不导入会演进的共享常量。

来源：Agent · retro.json
