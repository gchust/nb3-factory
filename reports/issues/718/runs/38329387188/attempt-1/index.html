问题 01 · 实现阶段

All ticket lifecycle notification effects failed with an invalid integer filter

本任务已处理

pnpm nocobase db sample built the demo accounts and tickets through the real services, but every notifyAssignee/notifyRequester effect failed after 1 attempt with 'Filter value is invalid for Field "id" of type "integer".' The sample data itself looked fine, so the failure was only visible in the lifecycle effect runs.

原因（实现者自述）
@nocobase/lifecycle's RepositoryLifecycleStore writes an effect run's transitionId with its key() helper (an all-digit id becomes a JavaScript number) and reads it back with String(). The application's own lifecycle migration declared lifecycleEffectRuns.transitionId as string(64); SQLite's TEXT affinity stored the bound number 3 as the text '3.0', and the next findTransition('3.0') passed a non-numeric string into the integer id filter of lifecycleTransitions.
处理方式
Declared transitionId as an integer column in 202611010002_create_lifecycle_tables.ts and pinned the contract with a migration field-type assertion plus a new end-to-end test, tests/logic/service-desk-notifications.test.ts, that drives the sample data and asserts the effects succeed and the in-app inbox items are delivered.
影响 / 代价：Roughly 15 minutes of extra work: the failure was reported as a plain message with no stack, so it needed a temporary throwaway test, a debug trace patched into the installed @nocobase/db repository validator (restored afterwards), and a column dump to locate the '3.0' value.来源：Agent · retro.json
问题 02 · 修复阶段

A fresh install showed an empty service desk: no sample data was ever loaded

本任务已处理

After pnpm start the ticket list was empty, ticket numbering started at #1, and the homepage 'open over 24 hours' count was 0 with no overdue reminder in the service desk Inbox. The sample-data registration existed but only ran when APP_SAMPLE_DATA=true, which neither the workflow nor the browser-acceptance scripts set.

原因（实现者自述）
Sample data was registered on the framework's sampleDataToken, which the framework runs only when app.sampleData is true (APP_SAMPLE_DATA). The harness runs plain db apply plus pnpm start and never sets it. A required seed could not replace it either: the seed task container (createTaskServiceResolver) only exposes idGeneratorToken, so a seed cannot resolve the users plugin service needed to create a login-capable account (the user and credential account rows) or drive the ticket lifecycle.
处理方式
Moved the sample onto an idempotent ensure that ServiceDeskSampleDataProvider.start() runs on a normal start (honoring an explicit app.sampleData=true, skipped under VITEST so the exact-count tests are not polluted), while keeping the sampleDataToken registration for APP_SAMPLE_DATA=true and db sample. It creates the demo accounts through the real users service and the tickets through the real ticket service, and backdates one open ticket past 24 hours and then asks the lifecycle to fire its reminder, so the homepage count and the Inbox reminder are both populated at start. Verified end to end against a production pnpm start: 3 tickets, 2 demo people on the desk, overview overdue=1, and a 'has been open over 24 hours' in-app item for the helpdesk.
影响 / 代价：未提供，不估算来源：Agent · retro.json
问题 03 · 修复阶段

A rejected attachment produced no failure feedback: the browser and the field both dropped it

本任务已处理

Uploading corrupt.png (a valid .png name and MIME type with junk bytes) showed 'corrupt.png: Done' and the file was stored; uploading unsupported.exe was removed with no 'unsupported format' message. The user could not tell that either upload had failed.

原因（实现者自述）
Two gaps on the same path. The raise form never passed FileUploadField's onError, so the field's accept/size rejections were silent; and FileUploadField.addFiles dropped a rejected file entirely instead of keeping it, so even a wired onError had no visible row. Nothing validated content: the accept rules and File.type trust the file name, and the upload route stores bytes without a signature check, so a renamed or corrupt file passed as a screenshot.
处理方式
Gave FileUploadField an optional validate hook that runs before upload, kept rejected files (both accept/size and validate) as visible failed rows with their message while still calling onError, added a page-local inspectAttachment that checks magic bytes against the claimed type, wired validate plus onError in the raise form to a dismissible destructive Alert and an error toast, and added en-US/zh-CN copy. Covered by a validator unit test and a FileUploadField component test that asserts a rejected file is shown and never uploaded.
影响 / 代价：未提供，不估算来源：Agent · retro.json

实现者补充建议

来自可选过程笔记，不代表已独立确认；相同建议引用上方评审，其余保留原文。

建议 01 · Skill 与文档

The lifecycle reference does not state the column types the repository store requires

可自动化

The app must declare the lifecycle log tables itself because @nocobase/lifecycle ships no migration. The reference explains the tables' fields and unique indexes but not that id-like columns are written as JavaScript numbers, so a string column silently corrupts transitionId into '3.0' and every effect fails its transition lookup. The failure is a plain message with no stack and surfaces only in the effect-run log.

建议改动

Add the required column types (numeric transitionId alongside the string record/lifecycle/effect columns) to the lifecycle reference, and note that a mismatch shows up as 'Filter value is invalid for Field "id" of type "integer"' in the effect run log.

来源：Agent · retro.json

建议 02 · api-ergonomics

Lifecycle effect failures are logged without a stack

可自动化

createLifecycleJobs reports a failed effect through the logger as a bare message (run id plus error.message). Distinguishing an application bug from a schema mismatch required re-running under a debugger/patched dependency.

建议改动

Include the error stack (or the error object) in the lifecycle jobs' failure log, at least at debug level.

来源：Agent · retro.json

建议 03 · api-ergonomics

FileUploadField hid every file it rejected

可自动化

When a file failed the accept rules or the size limit, addFiles only called onError and returned; no item was rendered, so a consumer that did not pass onError (or whose toast had already gone) saw the file vanish. The correct default for a file picker is a visible failed row naming the file and the reason.

建议改动

Have the field render rejected files as failed rows with their message by default and keep onError as an additional signal, which is what this application now does locally.

来源：Agent · retro.json

建议 04 · Skill 与文档

The sample-data reference does not say what a sample seed cannot do

可自动化

The guidance steers sample data to defineSeed({ sample: true }) or sampleDataToken, but a seed's task container exposes only idGeneratorToken, so sample data that must create a login-capable user (user plus credential account) or drive a lifecycle cannot be a seed. It also assumes APP_SAMPLE_DATA is set, which a plain db apply + start does not do.

建议改动

State in the sample-data reference that plugin services are unavailable in the seed task container and that a fresh-install sample needing them must be loaded from an application provider's start() (or a sampleDataToken with APP_SAMPLE_DATA set), and note that the standard harness never sets APP_SAMPLE_DATA.

来源：Agent · retro.json

建议 05 · api-ergonomics

A self-transition reminder defeats statusChangedAt-based overdue detection

可自动化

remindOverdue is a self-transition whose every planTransition unconditionally rewrites statusChangedAt, so a ticket open 26 hours stopped counting as overdue the moment its reminder fired. Overdue detection that reads only statusChangedAt cannot both remind repeatedly and stay true.

建议改动

Document that a periodic reminder must base its liveness on an immutable timestamp (createdAt) or another counter, not on the lifecycle's changedAt field, which every transition resets.

来源：Agent · retro.json

原始验收要求

我是IT服务台负责人，需要一个公司内部报修系统。员工提交问题、紧急程度和截图，服务台分派给工程师，工程师记录处理过程和解决办法，员工确认解决后关闭；仍未解决可以退回继续处理。 员工只看自己的工单，工程师只处理分派给自己的工单，服务台查看全部。新分派和处理结果及时通知相关人员，点击通知可以进入对应工单；超过24小时未解决时提醒服务台。首页展示待分派、超时工单和各工程师的工作量。

实际操作

  1. 以员工 employee@example.com 登录，打开 New ticket，填写标题/问题、Urgency=High、Category、Location，上传 sample.png 后 Submit ticket，创建工单 #5 并核对列表与详情中的附件预览。
  2. 在同一上传控件上传不支持的 unsupported.exe 与损坏的 corrupt.png，观察是否给出显式反馈；再上传 sample.pdf/sample.docx 核对被接受。
  3. 以服务台账号 nocobase 登录，在 Tickets 列表查看全部工单；打开工单 #1 用 Assign 对话框选择 Demo Engineer 分派，核对状态与历史 Awaiting assignment → Assigned。
  4. 对工单 #1 执行 Start handling、填写处理记录并 Add note，再 Mark resolved 并在 Record the solution 中填写解决办法，核对状态 In progress → Awaiting confirmation。
  5. 以工程师 engineer@example.com 登录，将工单列表切换为 Assigned to me，核对只出现分派给自己的工单；直接访问未分派给自己的 /main/tickets/4 验证不可见。
  6. 对退回收到的工单 #3 执行 Start rework、Add note、Mark resolved 并填写新的解决办法；打开 Inbox 核对分派/退回通知并点击通知进入对应工单。
  7. 以员工登录，在 Inbox 点击“Ticket #1 is resolved — please confirm”通知进入工单 #1 并 Confirm and close；对工单 #3 执行 Return for further work 并填写退回原因，之后再次确认关闭 #3。
  8. 以服务台登录，核对首页 Awaiting assignment / Open over 24 hours / Still open / Awaiting confirmation 与 Engineer workload 随操作更新；打开 Inbox 核对超过24小时提醒并点击进入工单 #1。
