# Server notes — document library

The default app server is empty apart from the framework. This feature adds one Collection pair, one
custom record access, one composite resource, four endpoints and one seed permission-set pair.

## Files

| Path                                                            | What it is                                                        |
| --------------------------------------------------------------- | ----------------------------------------------------------------- |
| `database/main/migrations/202611010001_create_documents.ts`     | Creates `documents` and `document_shares`                         |
| `database/main/seeds/202611010002_documents_permission_sets.ts` | Inserts the two permission sets idempotently                      |
| `database/seed-data/permission-sets.ts`                         | The grant definitions the seed and sample data share              |
| `server/documents-resources.ts`                                 | The `documents.readable` record access and the composite resource |
| `server/routes/documents.ts`                                    | The eight `/api/documents…` handlers                              |
| `server/routes/schemas.ts`                                      | The zod input/output schemas and the response types               |
| `server/providers/documents.ts`                                 | Registers the resources, the settings item and the sample data    |

`database/main/collections/` is generated by `pnpm nocobase db apply`; never edit it by hand.

## Read access is one custom record access, not the sharing plugins

`documents.readable` (`server/documents-resources.ts`) returns the records a person may read:

1. records they own (`ownerId == principal.id`), or
2. records that are published **and** not confidential, or
3. records explicitly shared with them through `document_shares`.

The public branch and the share branch both AND `confidential = false`. That is what makes a share of a
confidential document select nothing: the share row exists and is listed in the admin UI, but the
record never becomes readable to the shared person. This is enforced in the resolver itself, not by a
second rule, so no route or grant can forget it.

The built-in sharing-rules and restriction-rules plugins were deliberately **not** used. Those rules
gate an already-granted view; they cannot make a resolver return _nothing_ for a confidential document
while still listing the share, and expressing "published but not confidential" as a rule would spread
the confidentiality condition across the configuration instead of keeping it in one place.

## Grants

- `documents` is a **composite** resource with `view` / `create` / `edit` / `delete`. Each action binds
  its own database permission builder under key `documents`; they are kept separate because one builder
  applies its options and default to every action it declares.
- `documentsCreate` declares `.read('*')` as well as `.create([...])`. A `createOne` selects the row it
  wrote, and a policy whose `read` node is `false` makes that read throw `READ_FORBIDDEN`. The route
  re-reads the created row through the caller's own `view` policy regardless.
- The two seeded permission sets are `documents-editor` (page access + view/create/edit/delete) and
  `documents-reader` (page access + view). A reader's own `view` grant never implies edit: the list's
  `canEdit`/`canDelete` come from the caller's `edit`/`delete` decision, and the route's DTO policy
  falls back to `DENY_ALL` when the caller holds no grant (never `ALLOW_ALL`).

## The `/settings` page and the `documents.admin` settings item

`/settings` is an ordinary route whose `authz` is the `documents.admin` settings item. The item
declares two actions:

- `read` — open the settings page and read the staff list and the share lists.
- `manage` — create and revoke shares.

The UI gates share writes on `useCan({ resource: DOCUMENTS_ADMIN_RESOURCE, action: 'manage' })`; the
server checks the same action on `POST`/`DELETE /api/documents/:id/shares…`. Root bypasses both.

## Route prefix

`scope: 'api'` contributions all mount into one `Hono` router at `/` under `/api`. A route path
therefore carries its **full** path after `/api`: `/documents`, `/documents/:id`,
`/documents/:id/shares`, `/documents/:id/shares/:userId`. Writing `/` and `/:id` (the natural Hono
shape) makes `GET /api/documents` match `/:id`.

Every route declares `describeRoute()` and validates with `apiValidator()`. `CreateDocumentInput.body`
is `.nullable().optional()` because the form sends `null` for an empty body — an `.optional()`-only
schema rejects it with a 400.

## Authorization in the handlers

`authorization.require()` only accepts an effective `permit`. Composite/database checks come back as
`conditional`, so the handlers call `authz.authorize(...)` and accept `permit` **or** `conditional`,
then hand the resulting policy to the repository through `withPolicy(policy)`. A write naming a field
that is not in the policy's `fields` throws `RepositoryError('FIELD_WRITE_FORBIDDEN')`, which is why
each builder lists its writable fields.

## Seeds and source imports

`database/main/seeds/202611010002_documents_permission_sets.ts` is loaded by the runtime's task loader
through a plain `import()` of the source `.ts` file, so its relative import of the shared seed-data uses
the `.ts` extension. Node's native ESM resolution does not map a `.js` specifier onto a sibling `.ts`
file the way Vite and `tsc` do, and the failure only appears when the seed actually runs. `tsc`'s
`rewriteRelativeImportExtensions` rewrites the `.ts` specifier to `.js` in `dist`, so the same source is
correct for the compiled deployment.

`DocumentsProvider.boot()` guards on `container.has(authorizationToken)` because the authorization
plugin owns the service it registers into. The application always lists that plugin, but a test or an
application that composes the runtime without it must still boot; every provider's `register()` runs
before any `boot()`, so in a normal application the token is already present.
